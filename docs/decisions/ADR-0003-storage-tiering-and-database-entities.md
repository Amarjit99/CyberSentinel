# ADR-0003: Storage Tiering and Database Entity Architecture

**Status:** Accepted  
**Date:** 2026-10-16  
**Deciders:** Senior Software Architect, Data Platform Architect, QA Lead  
**Governing Conflict:** [CONFL-003](../audit/CONFLICT_REGISTER.md#confl-003-database-relational-entity-model-vs-monolithic-table-list-divergence)  

---

## 1. Context & Problem Statement

`00-MASTER-REQUIREMENTS-SPECIFICATION.md` §14 provided a monolithic list of 45+ tables, including high-volume event tables (`raw_events`, `normalized_events`). Attempting to store billions of raw telemetry events in a relational PostgreSQL database creates severe performance degradation, vacuuming bottlenecks, and index bloat. `docs/18-DATABASE-SCHEMA.md` proposed 17 core relational tables, while `docs/09-DATA-ARCHITECTURE.md` outlined a hybrid storage placement.

## 2. Decision

We formally ratify a **Polyglot Hybrid Storage Tiering Architecture**:

```text
                      INGESTION PIPELINE
                              │
             ┌────────────────┴────────────────┐
             ▼                                 ▼
   [ Raw Payload Storage ]           [ Normalization Engine ]
   - Object Store (S3/MinIO)                   │
   - Quarantined / Immutable                   ▼
   - Checksum: SHA-256               [ Search & Analytics ]
                                     - OpenSearch Cluster
                                     - Indices: canonical_events-*
                                                detections-*
                                                alerts-*
                                               │
                                               ▼
   [ Ephemeral Coordination ]        [ Transactional State Core ]
   - Redis                           - PostgreSQL 16+
   - Task queues, rate limits        - 17 Authoritative Tables (Doc 18)
   - Distributed locks               - RBAC, Incidents, Approvals, Audit
```

### Relational Schema (PostgreSQL Authoritative Core - 17 Tables)
1. `users`: System users and service identities.
2. `roles`: RBAC role definitions.
3. `user_roles`: User-to-role associations.
4. `connectors`: Telemetry source connectors and credentials references.
5. `events`: Metadata index and raw payload references (high-volume body in OpenSearch/Object Store).
6. `detections`: Rule match records and execution metadata.
7. `detection_events`: Many-to-many link between detections and source event references.
8. `incidents`: Authoritative incident lifecycle records.
9. `incident_detections`: Incidents to detections association with linking rationale.
10. `incident_entities`: Entities (users, hosts, IPs) linked to incidents.
11. `evidence`: Immutable forensic evidence artifacts with cryptographic checksums.
12. `incident_notes`: Analyst notes, investigations, and annotations.
13. `agent_runs`: Agent execution logs, prompt versions, and token budgets.
14. `agent_findings`: Structured claims and confidence scores generated by agents.
15. `response_proposals`: Proposed response actions with exact action payload hashes.
16. `approvals`: Human-in-the-loop approval signatures and policy references.
17. `response_actions`: Idempotent action execution tracking and rollback records.
18. `audit_events`: Tamper-resistant audit log for security-relevant events.

## 3. Consequences

### Positive
- PostgreSQL manages transactional ACID requirements (incidents, approvals, audit) without high-volume log bloat.
- OpenSearch delivers sub-second full-text and aggregation queries over billions of normalized telemetry events.
- Object storage guarantees immutable preservation of raw payloads.

### Negative / Trade-offs
- Requires dual-write / event-driven consistency mechanisms between PostgreSQL and OpenSearch.
